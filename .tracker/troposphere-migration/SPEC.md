# Spec: Migrate CloudFormation generation from Jinja templating to a troposphere object pipeline

## Problem Statement

darth-infra scaffolds and deploys ECS-based CloudFormation projects by rendering
Jinja2 text templates. Text-templating an indentation- and quote-sensitive
format has made the generator fragile: indentation is passed around as macro
arguments, YAML quoting and `Fn::Sub` interpolation are escaped by hand, and
logical-ID naming rules are split between templates and Python. Rendering bugs
surface at deploy time — the most expensive place — and ephemeral/preview
environments multiply that cost because every render is deployed many times.
Maintainers extending the generator (new resources, new conditionals) compound
the fragility with each feature.

## Solution

Replace the Jinja CFN templates with builders that construct templates as
troposphere object trees and serialize them to YAML. Conditional logic becomes
ordinary, testable Python; indentation and escaping bugs become impossible by
construction; property-name typos fail at build time instead of at changeset
time. The change is behaviorally invisible to deployed infrastructure: an
unchanged `darth-infra.toml` must produce a **no-op deploy** (empty changeset)
on every existing stack. The migration ships as one atomic cutover release.

## User Stories

1. As a project developer, I want `darth-infra deploy` on an unchanged config to produce a no-op deploy after upgrading the CLI, so that the migration never touches my running infrastructure.
2. As a project developer, I want logical IDs preserved exactly across the migration, so that CloudFormation never replaces my stateful resources (RDS, S3) and I never lose data.
3. As a project developer, I want rendered templates to remain valid, human-readable YAML with short-form intrinsics (`!Ref`, `!Sub`), so that I can still read and reason about what will be deployed.
4. As a project developer, I want template output written to the same paths as before, so that my scripts, docs, and muscle memory keep working.
5. As a project developer, I want my hand-edited `custom/overrides.yaml` left untouched by regeneration, so that my custom resources survive every render and deploy.
6. As a project developer with `templates/generated/` committed to git, I want the changelog to warn me about a one-time formatting diff, so that I'm not alarmed by a large but infrastructure-neutral diff.
7. As a project developer whose config values contain quotes, `${`, or other special characters, I want them serialized correctly by construction, so that no input of mine can corrupt a template.
8. As a project developer using preview environments, I want the same single template to serve prod, staging, and every ephemeral stack via Parameters and Conditions, so that previews keep exercising exactly what prod runs.
9. As a project developer, I want deploy-time validation to keep guarding required template content (e.g. SES policies when enabled), so that a generator regression is caught before it reaches CloudFormation.
10. As a maintainer, I want conditional resources expressed as plain Python on typed inputs, so that adding a feature no longer requires weaving logic through YAML text.
11. As a maintainer, I want all derivation logic (logical-ID pascalization, secret-name mangling, tag parameters, listener priorities) in one typed derivation layer, so that naming rules cannot drift between two places again.
12. As a maintainer, I want property-name and type mistakes to fail when the template object is constructed, so that I get feedback in a unit test instead of a failed changeset.
13. As a maintainer, I want the test suite to assert on template structure rather than rendered text, so that formatting changes never break tests and broken templates never sneak past string matches.
14. As a maintainer, I want `main` to remain pure-Jinja and releasable until the cutover release, so that unrelated fixes can ship mid-migration without exposing users to a half-migrated generator.
15. As a maintainer, I want the Jinja CFN templates deleted in the cutover release, so that no half-migrated pattern lingers to confuse future contributors.
16. As a release manager, I want a pre-release verification script that runs AWS CLI changeset diffs against existing real stacks and reports whether any infrastructure changes would occur, so that the no-op-deploy contract is checked against ground truth before shipping.
17. As a release manager, I want the cutover published as a minor version with an explicit changelog entry, so that users get an honest signal proportionate to the change.
18. As a teammate on an older CLI version, I want the existing version-floor ratchet to lock me out of projects regenerated by the new CLI, so that mixed-version teams can't silently regenerate with different pipelines.
19. As a CI operator, I want `cfn-lint` run over rendered fixture output, so that template validity is continuously checked without requiring AWS credentials.
20. As a future contributor, I want the migration's rationale and constraints captured in the ADR and glossary, so that I understand why troposphere was chosen and which invariants are permanent contracts.

## Implementation Decisions

- **Object layer**: troposphere `Template`/resource classes, serialized to YAML
  via troposphere's cfn-flip integration (short-form intrinsics). New runtime
  dependencies: `troposphere`, `cfn-flip`. Escaping to raw dicts is permitted
  only for constructs troposphere cannot model, and is treated as a smell.
- **Primary seam (new)**: a pure function
  `build_project_templates(config: ProjectConfig) -> ProjectTemplates`, where
  `ProjectTemplates` maps relative output paths to troposphere `Template`
  objects (root stack plus one per service). No I/O. This is the single
  structural surface for tests and deploy-time validation.
- **Derivation layer**: the loose context dict built by the current
  `_build_context` is replaced by frozen dataclasses (`RenderContext`,
  `ServiceRenderContext`, `TagParameter`, path-rule context, …) produced by one
  derivation function from `ProjectConfig`. All computed values port 1:1 —
  same computations, typed containers. Logical-ID pascalization and
  secret-name mangling (`replace('_','')`-style quirks included) live only
  here.
- **Logical IDs are a permanent public contract.** Every builder must
  reproduce today's logical IDs exactly. A changed logical ID is a
  resource-replacing bug, not a cleanup opportunity.
- **The generator's file-writing entry point** (`generate_project`) shrinks to
  build → serialize → write. Its user-visible behavior is frozen: same output
  paths (`templates/generated/root.yaml`,
  `templates/generated/services/{name}.yaml`), write-once
  `templates/custom/overrides.yaml`, user-data script copying, README
  rendering, config/schema emission.
- **Deploy-time validation** keeps its role in the deploy flow but asserts
  structurally on built template objects (e.g. the SES policy object with its
  action list exists when `enable_ses_send_email` is set) instead of
  substring-matching rendered text.
- **Prose templates stay Jinja**: `README.md` generation is text and remains
  text-templated. Only the CFN YAML templates are migrated and then deleted.
- **One template serves all environments** via Parameters and Conditions —
  render-time environment specialization is prohibited, preserving
  template parity between prod and ephemeral/preview stacks.
- **Backwards-compatibility contract**: no-op deploy (empty changeset) for
  unchanged configs on existing stacks. Textual differences in rendered
  templates are permitted; resource modification or replacement is not.
- **Verification of record**: AWS CLI changeset diffs (create changeset
  without executing; inspect for infrastructure changes) against existing real
  stacks, run pre-release. Provide a small script/command for this check.
- **Rollout**: atomic cutover on a branch; `main` stays pure-Jinja and
  releasable throughout; one minor-version release swaps the pipeline and
  deletes the Jinja CFN templates. The existing CLI version floor auto-ratchet
  needs no changes.

## Testing Decisions

- Good tests assert **external behavior at the primary seam**: given a
  `ProjectConfig`, the built templates contain the expected logical IDs,
  properties, parameters, and conditions (via `Template.to_dict()`). Tests
  never assert on rendered YAML text, key ordering, or formatting, and never
  reach into builder internals or the decomposition of builder functions.
- The existing generator tests that grep rendered text (CloudFront/ALB,
  preview environments, secret validation) are ported to structural
  assertions at the new seam, preserving their scenarios and config fixtures —
  the fixture-building style in the current generator tests is the prior art
  to follow.
- `generate_project` keeps a small smoke suite: files land at the frozen
  paths, output parses as YAML, `custom/overrides.yaml` is not overwritten
  when present.
- `cfn-lint` runs over rendered fixture output in CI as the ongoing template
  validity check (hermetic, no AWS credentials).
- The pre-release live check (changeset diff on real stacks) is scripted but
  is a release gate, not part of the CI test suite.

## Out of Scope

- Property-level template overrides (deep-merging user patches from
  `darth-infra.toml` onto generated templates) — deferred to a post-migration
  release.
- Any change to the `darth-infra.toml` schema or config model semantics.
- TUI changes of any kind, including hardening.
- Per-environment render specialization (explicitly prohibited, not just
  deferred).
- Changes to the deploy/changeset/recovery layer beyond the validation
  function's inspection mechanism.
- Purpose-built verification stack matrices or offline golden-compat suites
  (considered and declined; verification is against existing real stacks).

## Further Notes

- See `docs/adr/0001-troposphere-template-generation.md` for the decision
  record and rejected alternatives (CDK, parse-and-mutate, plain dicts), and
  `CONTEXT.md` for the glossary terms used here (*no-op deploy*, *logical ID*,
  *rendered template*).
- Accepted risks: verification coverage is capped at the feature combinations
  present in the real stacks diffed pre-release; users who committed rendered
  templates see a one-time formatting diff.
- Troposphere may lag brand-new CloudFormation resource types; the raw-dict
  escape hatch covers gaps but each use should be revisited.
