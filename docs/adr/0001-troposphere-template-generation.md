# 1. Generate CloudFormation templates via troposphere instead of Jinja

Date: 2026-07-13

## Status

Accepted

## Context

CloudFormation templates were produced by rendering Jinja2 text templates
(`templates/cfn/*.j2`). Text-templating an indentation- and quote-sensitive
format accumulated fragility: indentation passed as macro arguments, hand-rolled
escaping for YAML quoting and `Fn::Sub` interpolation, and logical-ID naming
rules split between templates and Python. Errors surfaced at deploy time —
expensive because ephemeral/preview environments create stacks from the same
template many times per render.

Alternatives considered: AWS CDK (rejected: owns the deployment model and emits
hashed logical IDs, incompatible with this tool's changeset-review and recovery
layer); parse-and-mutate static YAML fragments (rejected: keeps logic split
between files and code); plain dicts with intrinsic helper functions (viable,
but forgoes construction-time property validation).

## Decision

Templates are built as troposphere object trees and serialized to YAML
(troposphere → cfn-flip, short-form intrinsics). The Jinja-era loose context
dict (`_build_context`) is replaced by typed, frozen dataclasses
(`RenderContext` and friends) produced by a single derivation function from
`ProjectConfig`; all naming rules (logical-ID pascalization, secret-name
mangling) live only there. Deploy-time template validation and generator tests
assert structurally on the built objects, never on rendered text.

Backwards-compatibility contract: rendering an unchanged `darth-infra.toml`
must produce a **no-op deploy** (empty changeset) on every existing stack.
Logical IDs are a permanent public contract. Textual differences in rendered
YAML are explicitly permitted.

Rollout: single atomic cutover release (minor version bump); `main` stays
pure-Jinja until then; the `.j2` CFN templates are deleted in the cutover
release (`README.md.j2` remains Jinja — prose, not YAML). Verification of
record: `aws cloudformation` changeset diffs against existing real stacks,
run pre-release, expecting no infrastructure changes.

Frozen in the cutover release: `darth-infra.toml` schema, TUI, output paths
(`templates/generated/root.yaml`, `templates/generated/services/{name}.yaml`),
the write-once `templates/custom/overrides.yaml` behavior, and the invariant
that one template serves all environments via Parameters/Conditions (no
render-time environment specialization). Property-level template overrides are
deferred to a post-migration release.

## Consequences

- Whole bug classes (indentation, quoting, `${` escaping) are eliminated by
  construction; property-name typos fail at build time via troposphere
  validation instead of at changeset time.
- Rendered output formatting changes; users who committed
  `templates/generated/` will see one-time large diffs. Accepted, since the
  files are regenerated build artifacts and the no-op-deploy contract holds.
- Verification coverage is capped at the feature combinations present in the
  real stacks diffed pre-release; config permutations no real stack uses are
  unverified against live CloudFormation. Accepted trade-off.
- New runtime dependencies: `troposphere`, `cfn-flip`. Troposphere may lag
  brand-new CFN resource types; escape to raw dicts is available but should be
  treated as a smell.
- **Spec lag fails closed and silent, and it applies to properties, not just
  resource types.** Troposphere validates against a bundled spec snapshot and
  rejects unknown kwargs, so a property AWS has added but troposphere has not
  picked up cannot be set — and the resulting template is simply missing it, with
  no error. This bit the dedicated-ALB listeners: CFN accepts `Tags` on
  `AWS::ElasticLoadBalancingV2::Listener`, troposphere 4.10.2 does not list it,
  and the tags silently vanished. The workaround is a subclass extending `props`
  (see `_TaggableListener`, `_LegacySecurityGroupEgress`), but it only helps
  where someone notices the absence. Pin cfn-lint at a version at least as
  current as the CFN registry — a stale linter will validate the omission as
  correct rather than flagging it.
- The CLI version floor auto-ratchets on render, so projects touched by the
  post-cutover CLI can no longer be regenerated by pre-cutover CLIs.
